DeadlineFit

DeadlineFit is a deterministic deadline feasibility checker. It turns a deadline, task estimates and hours per day into a day-by-day plan and one key metric: how much aggregate estimation error the plan can absorb before it stops fitting.

Main pieces

  • index.html — the single-screen form and result shell.
  • src/app.js — reads the form, calls the planner, renders status, tolerance and allocation.
  • src/planner.js — validates inputs, counts calendar days, calculates tolerance and allocates work.
  • test/planner.test.js — verifies the deterministic rules, including the UK DST boundary.

Run it again

Requires Node.js 20+. No API keys, database, backend service or network connection are required.

npm start

Then open http://localhost:4173. Run npm test for the planner checks.

One action through the app

The route below follows the real Build plan action from input to visible result.

Reference route — 3 stops

1 · Input and submitsrc/app.js

Search for form.addEventListener('submit'. This gathers the deadline, hours/day and task rows, then calls the planner.

2 · Core logicsrc/planner.js

Start at buildPlan(). The key formula is calculated here, and feasible plans are passed to allocateTasks().

3 · Outputsrc/app.js

Search for renderResult() and renderAllocation(). These turn the deterministic result into Feasible/Impossible, tolerance and the day-by-day plan.

To change this, start here

  • Change the calculation or allocation rule → src/planner.js.
  • Change result wording or formatting → src/app.js.
  • Change layout, spacing or responsive styling → styles.css.
  • Add or adjust rule verification → test/planner.test.js.

A practice to reuse

The project turned the distinctive claim into a precise formula and observable transitions before polishing the UI. The evidence is split across devpost/prd.md, src/planner.js > buildPlan(), and the planner tests. On another project, define the one behaviour that proves the idea, make its output measurable, and verify it before adding surrounding features.

Why the DST test matters

The plan counts calendar dates, not 24-hour blocks. Testing across the UK clock change protects the deadline calculation from an implementation shortcut that could otherwise create a one-day error.
